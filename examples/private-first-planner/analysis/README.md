# Cube selection and semantic-query fallback

This report-planning entry lets a private planner reuse a cube when it covers the
whole question. If not, a separate private data-worker component proposes a
semantic aggregate query. The host executes through its existing Wren connection,
checks evidence and issues report capabilities. It never silently drops a requested
dimension to fit a cube or creates a permanent cube from a single question.

## Ownership and entry points

| Unit | Implementation | Responsibility |
| --- | --- | --- |
| Private planner | Warble `select_report_source` | Interpret intent; select cube/fallback; ask when definitions or intent are ambiguous |
| Private data worker | Warble `plan_semantic_query` | Select an authorized semantic model/view/join binding; preserve requested measures, dimensions, filters and period |
| Host session | `host/report.mjs` | Validate proposals; own clarification state, authorization, execution and report issuance |
| Host Wren adapter | `host/report-wren.mjs` | Use existing `ask_data`, `continue_task`, `get_evidence` and session revisions; no separate MCP server |
| Runtime binding | `host/report-runtime.mjs` | Bind two independently configurable pi decision contracts to the existing private model and host Wren client |
| Report projection | `analysis/report.mjs` | Validate aggregate shape and produce a disclosure-safe capability/data projection |

The Warble profile and pinned compiled artifacts live under `analysis/behaviors/`.
Components contain behavior, while the host owns state and effects. Both component
contracts work through the existing `PiPlanner`; neither has cloud or connection
tools. Live binding is explicit; importing modules or running evals never calls a
paid endpoint.

```js
import {createReportRuntime} from '../host/report-runtime.mjs';
const runtime = await createReportRuntime(config, policy);
try {
  let state = await runtime.session.submit('Revenue by channel last quarter');
  // If waiting_for_user, show state.question and pass the actual user's answer:
  // state = await runtime.session.answer(state.question_id, answer);
  // completed => state.report.{capabilities,payload}
} finally { await runtime.close(); }
```

This is an additive host report entry, not a silent replacement for the existing
scalar/week conversation controller, revenue replay runner or its design prompt.
The current interactive revenue HTML remains unchanged. A UI/pi conversation driver
can call submit/answer/snapshot/cancel; questions have unique IDs and may originate
from planner, worker planning or Wren execution. Only a matching Wren continuation
uses `continue_task`. Three planner/worker calls and four execution attempts bound
one report task. Source changes, denial, invalid results and cancellation never
produce a completed report. Cancelled uncooperative effects cannot overlap a new
submit or publish late results; close the runtime when abandoning a report task.

## Trusted registry and semantic plans

`analysis/contracts.mjs` defines the closed shapes. The deployment supplies a fresh,
authorized registry with a revision and canonical public measure/dimension IDs.
Each source declares cube/semantic kind, revision, measure/dimension coverage,
grains, half-open UTC date coverage, existing Wren capability and private metadata.
Source bindings must already capture confirmed definitions and allowed joins.
They are not generated by this workflow; registry loading from arbitrary MDL and
automatic join/metric discovery are separate deployment work.

The planner sees the capability catalog without private metadata or Wren capability
names. The worker receives only matching semantic source candidates plus their
private metadata. Every query specifies measures, grouping dimensions, calendar
grain, half-open date bounds and dimension-value filters. An insufficient cube
selection falls through to the worker with the **same request**. The worker cannot
add raw fields, alter scope, fabricate a join or issue SQL. It chooses a declarative
semantic plan; Wren's private agent then generates/executes semantic SQL using its
existing tool and policy boundary. A cube ID is never treated as a SQL table.

The source catalog must be complete enough to distinguish unavailable data from
ambiguous intent. A planner must ask about an unclear metric definition instead
of assuming one. If no authorized source covers an admitted request, the host
returns unsupported without querying. Source coverage is not proof of result
completeness: evidence still needs verification after execution.

## Host policy is mandatory

`createReportRuntime(config, policy)` requires these deployment-owned functions:

- `loadRegistry()`: fresh, authorized registry; private metadata stays local.
- `authorize({phase, plan?, data_version?})`: recheck at planning, before each
  query/continuation and before report issuance. Only boolean true permits it.
- `verify({plan, source, execution})`: validate actual private execution evidence,
  including business definitions, filters, UTC period, grain, source revision,
  truncation/row limits and completeness. Return `verified`, `complete`,
  `source_revision`, `query_digest` and `result_digest`; digests bind the receipt to
  the exact admitted query/result. This receipt must never come from a model.

There is deliberately no optimistic default verifier. The Wren adapter fetches
`get_evidence` and checks it matches the returned result; that alone does not prove
arbitrary business semantics or complete coverage. Existing scalar/week evidence
checks are not silently relabeled as multidimensional report verification. A
production deployment supplies its domain verifier; missing verification fails.
The scripted fixture verifier checks its synthetic data for deterministic testing,
not as a substitute for a real database oracle.

The host requires unique period/dimension cells, exact columns, finite numeric
values (or null), proper bucket alignment and filter scope. It verifies a requested
ratio against its numerator/denominator when both are included. Sum, ratio-of-sums
and non-additive measures have explicit aggregation semantics. This is bounded
aggregate reporting (four dimensions, eight measures, 5,000 rows, 64 KiB), not raw
record export. Partial week bucket labels may precede the filter lower bound;
source timestamp filtering must still match the requested half-open range.

## Capability output and compatibility

`aggregate-report/1` contains an honest source kind (`cube` or `semantic_query`),
opaque binding/revision, query/data digests, actual queried dimensions and values,
measures/units, period, applied filters and cross-dimension breakdowns. It includes
no private source name, SQL, connection fields, metadata or execution evidence.
`aggregate-report-data/1` contains the authorized aggregate table. No undeclared
hierarchy or broader time coverage is advertised. Ratios permit roll-up only when
the numerator and denominator are also in the snapshot; non-additive measures do
not. Null is unknown/undefined, not zero. Refresh requires a host rebind.

This general contract is distinct from the existing fixed revenue snapshot
`revenue-report/1`. Do not put product/profit results into that old runtime or invent
a cube ID to make it accept a fallback. A frontend must explicitly consume the new
contract or a deployment must provide a verified projection to the old revenue
shape. The planning entry produces capabilities/data; it does not invoke a designer or
change old HTML. The optional browser binding below supplies bounded offline
aggregation to free frontend code.
A completed private report does not grant cloud disclosure. Feed only an authorized
projection through the existing ExportBroker and its explicit grant/freshness checks
before any future cloud use.

## Independent evaluation and CI

From the example root, use new output directories:

```sh
node analysis/eval.mjs planner /absolute/new/planner-results
node analysis/eval.mjs worker /absolute/new/worker-results
node analysis/eval.mjs host /absolute/new/host-results
node --test analysis/test/*.test.mjs
node analysis/behaviors/compile.mjs --check
```

The shared offline gate runs all three suites and tests; the behavior gate checks
the pinned Warble artifact. Transport tests exercise both components through real
pi with scripted local SSE, and the Wren adapter through scripted tool responses.
They verify sequencing/contracts, not real Nemotron accuracy or new real-database
fallback acceptance. Reuse, channel/product fallback, ambiguity, missing measures,
invalid plans/results, authorization, revisions, continuation and cancellation are
covered. Preserve old model runs and report artifacts as separate baselines.

## Interactive offline binding

`analysis/browser/export.mjs` exports an admitted report with a freely authored
HTML/CSS/JavaScript spec and its matching data bundle. Layout and chart rendering
remain frontend code; the trusted runtime supplies aggregation, not a renderer.

```js
import {aggregateReportDocument} from './browser/export.mjs';
const html = aggregateReportDocument(spec, bundle, state.report);
// In the sandboxed frontend:
const answer = await window.reportData.query({
  lower: '2026-04-01', upper: '2026-07-01', dimension: 'country',
  filters: {}, path: [],
});
// answer.result: totals, groups, trend, empty, unavailable
```

`window.reportData.capabilities` and `.catalog` declare the available metrics,
units and dimension values. Filters select arrays of declared values; chart clicks
append `{dimension, value}` to `path` and select a declared breakdown dimension.
Roll-up removes a path item, and reset restores the frontend's declared initial
state. Cross-dimension breakdown is not an invented hierarchy. KPI cards, filters,
period controls, chart labels and visible drill state must all use the same query.
Only snapshot-covered, grain-aligned periods are accepted. Ratio-of-sums requires
its components; unknown/non-additive multirow values return null, not zero.

The `aggregate-query/1` response includes request and data-version identities.
Free frontend code must suppress stale responses if it adds asynchronous effects.
The runtime is an offline snapshot adapter: no network, WASM, credentials or live
refresh. Future host queries require a separate authorized rebind/transport.
Structural export validation checks identity and capabilities; it does not confer
semantic verification, authorization or cloud disclosure. Only export reports
already admitted by the host and match `bundle.payload` to the report payload.
Decimal aggregation uses compensated floating sums, not arbitrary precision.

The offline gate tests capability/identity rejection and aggregation semantics;
the browser gate exercises actual file HTML, sandbox execution and disabled
network. Existing fixed revenue exports and their baselines remain unchanged.
Planner/worker clarification may include an explanatory text `reason`, but must
still contain no executable request or source selection.

## Bounded serve-agent report partitions

The released serve-agent capability limits each result to 100 rows. A larger
report therefore needs deployment-owned partitioning; requesting an arbitrarily
large table or adding LIMIT cannot establish complete coverage.

`createReportRuntime` accepts an optional `partitionPolicy` in its third argument:
`periods({plan, source})` returns at most 24 contiguous, non-overlapping periods of
the original grain that exactly cover the request. The host preserves every other
query field. Choose the width from known dimension cardinality; an oversized
partition must fail rather than silently truncate. Week splits must align to week
boundaries. This first implementation partitions time only.

`project({plan, source, execution})` must independently verify each raw service
result and return `{verified, complete, source_revision, query_digest,
raw_result_digest, result}`. `result` is its canonical report table. Serve agent
uses host-labelled `c1`, `c2`, ... columns and can represent decimals as strings;
these must be mapped under a verified binding, never by guessing from model aliases.
There is no permissive default projector. Final report verification still runs.

The executor preserves individual raw results, evidence and source plans in a
private `partitioned-report-evidence/1` ledger. Synthetic aggregate references are
host-local and must not be passed to Wren get_evidence. Each child fetches real
service evidence first. A service clarification pauses at the current partition;
its continuation resumes without replaying completed partitions. Any failed,
unverified or overlapping part prevents publication of the whole report.

The service worker receives the admitted source binding metadata privately to
resolve canonical definitions; the outer planner and dashboard do not. Explicit
source and period instructions also survive paginated context indexes. This does
not add SQL access to the caller, bypass service policy or publish private metadata.
